  What's in place:
  - gfx/skia/gdi/SkGDIDocument.{h,cpp}: a new Skia document backend,
    SkGDI::MakeDocument(HDC, Options), built like SkPDF. It lives outside the
    vendored Skia tree, and I added it to both gfx/skia/moz.build and
    generate_mozbuild.py so a Skia update won't drop it. Each page is recorded
    into an SkPicture and replayed twice:
    a. Analysis pass: sorts every draw into "GDI can do it", "GDI can do it if
       nothing is underneath", or "GDI can't do it", and collects the page area
       GDI can't draw. This follows cairo's paginated approach.
    b. Emission pass: sends the supported draws to the DC as GDI calls:
       - Shapes: solid fills go through PolyDraw + FillPath (conics are
         converted to cubics), and strokes are turned into fills by Skia first.
       - Clips: SelectClipPath / IntersectClipRect.
       - Images: opaque images go through StretchDIBits with a world transform.
       - Gradients and patterns (any opaque non-solid paint): rasterized just
         for the shape's bounds, then clipped to the shape.
       - Translucent draws with nothing underneath are blended against the white
         page and emitted as vectors, like cairo does.
       - Text: ExtTextOutW with glyph indices, using a GDI font from DWrite's
         IDWriteGdiInterop. To be sure glyph ids match, it checks that GDI and
         DWrite see the same font file (it compares the head, maxp and name
         tables). Web fonts, variable fonts, emboldened text and stroked text
         are drawn as filled outlines instead. Color glyphs are rasterized.
    c. Raster fallback: the area GDI can't draw is rasterized from the picture
       at 300 DPI by default, in strips to limit memory, and pasted on top. This
       covers blend modes, opacity, masks and filter layers.

    Layers that are composited normally become pass-through, so their contents
    are still drawn as vectors; other layers are rasterized.
  - PrintTargetWindows: uses the new document when the new pref
    print.windows.skia-gdi.enabled is on (default true); otherwise it keeps the
    existing cairo path, so you can compare the two. The page canvas is the
    printable area in printer pixels, which is the space Gecko already draws in
    on Windows. A second pref, print.windows.skia-gdi.raster-dpi, controls the
    fallback resolution.

  Known gaps:
  - Raster fallback areas are pasted at lower resolution, so there may be small
    seams where they meet the vector content around them.
  - Translucent images and AlphaBlend always go through the fallback path.
  - Backdrop filters aren't handled.

  Next steps would be to fix the include, finish the build, and print some test
  pages, comparing against the cairo path with the pref off.

     per run and on failure just returns an error, with no retry as outlines.
     Now, once the font and transform are set up, a failed call no longer
     triggers the outline retry, as in cairo.
  2. Font size rounded to whole device pixels: not in cairo. Cairo creates the
     GDI font at 32 times the size and scales it back down with the world
     transform, which gives 1/32-pixel precision for both size and glyph
     positions. I've copied that with a kTextLogicalScale = 32 constant. Even on
     a large 600 DPI page, the coordinates stay far within the limit I clamp
     to.
  3. Font identity: worse in cairo.
     _cairo_dwrite_scaled_font_create_win32_scaled_font uses the result of
     ConvertFontFaceToLOGFONT with no check, so a wrong match prints wrong
     glyphs. My comparison of the head, maxp and name tables at least catches
     most mismatches and draws those runs as outlines instead. The remaining
     risk is fonts packed together in one .ttc file with identical tables, which
     would get past the check, but cairo already has that problem without any
     check.

  someone prints with it on a real Windows machine.
